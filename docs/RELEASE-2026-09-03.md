### 4. 部署脚本（`scripts/deploy-mvp.sh`，`23a0892`）

| 变更 | 说明 |
|------|------|
| **修复**：ops public 漏同步 | 脚本只 rsync 了 web/storefront 的 `public/`，**`apps/ops/public/` 从未同步**——`ops.szchada.top/brand/*`（favicon、touch icon）自 ops 上线以来一直 404。补齐同款 `--delete` 行 |
| 有界两波并行构建 | packages + `prisma generate` 仍串行（apps 依赖其 dist）；随后 api+web 一波、storefront+ops 一波（每波 ≤2 个，内存峰值减半），每个 app 在独立子壳里 source 自己的 `.env` 并 export 覆盖项，互不泄漏 |
| 实测 | 构建段（packages→四 app）**2 分 24 秒**（CPU 246%）；对照今晨串行版同段约 20+ 分钟。无界四开实测过一次墙钟 67 分钟、CPU 仅 ~10 分钟——日常工作机内存/IO 争抢（疑似中途合盖睡眠），故收敛为每波 2 个 |
| 为什么不用 turbo 缓存 | ASSET_PREFIX 这类 env 串台正是 2026-09-02 `/app` 资产事故的成因；turbo 只有把全部 env 声明进任务哈希才能安全缓存，声明不全时缓存命中会回错构建（「200 但内容错」一类故障）。并行化拿到大部分收益，零缓存风险 |

### 本轮发现并修复的生产故障

**ops.szchada.top/brand/* 图标 404（自 ops 上线起）**：`deploy-mvp.sh` 为 web/storefront 各有一行 `rsync public/`，唯独漏了 ops——图标文件从未上过服务器，公网三个路径返回同一个 404 HTML（md5 相同暴露了这一点）。修复：补 rsync 行（`23a0892`）+ 立即手动补同步 + `pm2 restart drsell-ops`，修复后 checksum 全部对齐。教训与上次「健康检查绕过 nginx」同源：**上线时没有对静态资产做内容级断言**——本次冒烟已把图标 checksum 纳入清单。
