## Context

服务链路只认「回答次数」，从不认「订阅状态」。生产上
`chatbotdomaintest` 的 `currentPeriodEnd` 停在 2025-08-25，一年多未续，
应用照常服务——因为这条判定压根没写。

三个既有约束决定了本变更的形状：

1. **本地订阅镜像不可全信。** `app_subscriptions/update` 是唯一的同步渠道
   （`ADR-14`），而它 2026-09-09 前因 `SHOPIFY_API_SECRET` 错误全线 401，
   镜像滞后了一年多。现在虽已能收，但仍依赖 `SHOPIFY_API_SECRET_PREVIOUS`
   （Shopify 仍用旧密钥签），属未收尾状态。**拿一份刚刚才恢复同步的镜像去停服，
   是本变更最大的风险。**
2. **仓库没有任何调度器。** 无 `@nestjs/schedule`、无 cron。上一个 change
   明确把「任务队列基础设施」列为 Non-Goal，理由是当前量级下是纯负债。
   而「连续三天提醒」天然需要按天触发。
3. **出站通道不存在。** `sendDunning` 排一条 `KnowledgeSyncJob` 给一个不存在的
   worker，催缴从未发出。`apps/api/src/mail/` 有模块，但催缴路径没用它。

## Goals / Non-Goals

**Goals:**
- 失效订阅不再免费获得服务
- 试用期不消耗计费周期
- 到期后 2 天宽限，宽限内不中断
- 到期前三天连续提醒，且真的送达
- 付款恢复即自动解冻，不需人工

**Non-Goals:**
- 套餐价格与档位（`ADR-14` 已定）
- Shopify 托管计费的下单流程（商家在 Shopify 界面选，不走本服务）
- 多店计费分摊（`isBillingShop` 已有）
- 运营台手工冻结/解冻（`ops` 已有，本变更不改）
- 通用任务队列（见 D4，只引入最小的按天触发）

## Decisions

### D1：闸门放在配额检查之前，与接管闸门同一处

`AdpService.proxyChatSse` 里已经有一道 `human` 接管闸门，位置在
`quota.assertWithinQuota` 之前。订阅闸门放在同一段。

**理由**：两道闸门的语义一致——「这通对话根本不该产生上游成本」。放在配额之后
会让被拦下的对话仍然扣额度，商家为没得到的回答付费。

**代价**：`AdpService` 多一个依赖（订阅状态）。可接受：它已经依赖 `QuotaService`，
两者本就是同一类判定。

### D2：试用期排除靠「周期锚点后移」，不引入新状态

计费周期的锚点从 `trialEnds` 起算而非安装日。试用期内 `periodStart` 返回
`trialEnds`（或不返回周期），额度按试用规则单独计。

**理由**：不新增状态位就能表达「试用不消耗周期」，`trialEnds` 字段已存在。

**待决**：试用期内的额度是多少？按 basic 档给、还是单独一个试用额度？
`@drsell/shared` 的 `PLANS` 目前没有试用档。**这是产品决策，需要你定。**

### D3：宽限窗口派生，不新增字段

宽限截止 = `currentPeriodEnd + 2 天`，按需计算，不落库。

**理由**：落一个 `gracePeriodEnd` 字段就多一处需要与 `currentPeriodEnd` 保持
一致的真相；派生值不可能不同步。而且「宽限窗口不可被刷新」这条需求，
派生天然满足。

**代价**：宽限长度若将来要按店定制，就得改成落库。目前是全局常量。

### D4：按天触发怎么来——三个选项，需要你定

「连续三天提醒」必须每天判定一次。仓库没有调度器，可选：

| 方案 | 做法 | 代价 |
|---|---|---|
| **a. 引入 `@nestjs/schedule`** | 进程内 `@Cron('0 3 * * *')` | 多实例会重复触发，需要去重（本 change 的去重需求正好覆盖）；进程重启期间错过的当天不补 |
| **b. 惰性触发** | 商家或顾客访问时顺带判定并补发 | 零基础设施；但**没有访问就不提醒**——而临近到期的店恰恰可能没人访问，正是最需要提醒的时候 |
| **c. 外部 cron 打一个受保护端点** | 服务器 crontab → `POST /internal/cron/expiry-notices` | 简单可靠；但多一处部署外的配置，`deploy-mvp.sh` 不管它，容易漂移（本仓刚吃过提示词漂移的亏） |

**倾向 a + 本 change 已有的持久化去重**：它把触发和去重都留在代码里，
`deploy-mvp.sh` 一并带走，不产生部署外的配置。b 的失效场景恰好是最关键的场景，
应排除。

**这个选择需要你拍板**，它决定了任务清单的形状。

### D5：解冻依赖 webhook，宽限窗口是它的安全垫

「付款解冻」的知情渠道只有 `app_subscriptions/update`。webhook 迟到或丢失时，
2 天宽限窗口给同步留出时间——这也是宽限存在的第二个理由（第一个是给商家
反应时间）。

**前置条件**：该 webhook 必须可靠。它现在依赖 `SHOPIFY_API_SECRET_PREVIOUS`
才能通过验签，属未收尾状态。**本变更实施前应先把密钥问题收尾**，否则等于
在一个仍会漏消息的通道上建停服判定。

### D6：先只读观测，再开闸

停服是不可逆的商家体验损失，而镜像刚从一年滞后中恢复。

实施顺序 SHALL 是：先把判定逻辑跑成**只记录不拦截**（记录「若开闸会拦下哪些店、
原因是什么」），观察一段时间确认没有误判，再真正开闸。

**理由**：`chatbotdomaintest` 的 `currentPeriodEnd` 停在一年前——如果直接开闸，
这个店立刻停服，而它可能只是镜像没同步。误停一个真实付费商家的代价，
远大于多让失效商家白用几天。

## Risks / Trade-offs

**R1 — 误停付费商家（高）**
本地镜像刚从一年滞后中恢复，且 `app_subscriptions/update` 的可靠性尚未收尾。
按一份可能仍不准的镜像停服，会直接伤到付费商家。
缓解：D6 的只读观测期；2 天宽限；商家端明确显示原因与恢复入口。

**R2 — 密钥前置未收尾（高）**
`SHOPIFY_API_SECRET_PREVIOUS` 目前是 webhook 能通过的必要条件。
Shopify 何时切到新密钥未知，切换时若没人注意，webhook 会再次全挂，
而这次的后果是「解冻消息收不到 → 已付款的商家被停服」。
缓解：实施本变更前先收尾密钥；`accepted with PREVIOUS secret` 的 warn 已在，
需要有人真的去看。

**R3 — 提醒渠道不存在（中）**
`sendDunning` 从未真正发过邮件。「提醒要真正送达」这条需求实际要求先把出站
通道做出来，工作量可能大于闸门本身。
缓解：应用内提示不依赖出站通道，可先落地；邮件作为第二步。

**R4 — 多实例重复触发（中）**
若选 D4-a，多个 API 实例会同时触发当天的提醒。
缓解：持久化去重（本 change 的需求已覆盖），去重键为「店 + 周期 + 档位」。

**R5 — 试用额度未定（中）**
`PLANS` 里没有试用档。D2 的实现依赖这个决策，未定则无法完成。

**R6 — 停服话术会暴露商家商业信息（低）**
顾客侧的说明不得暴露商家的套餐、欠费、用量——那是商家的商业信息。
现有「额度耗尽」话术已经守住了这条，停服话术照同样标准写。
