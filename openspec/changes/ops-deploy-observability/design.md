## Context

`DEPLOY.md` 记的是「配置应该是什么」，但两次事故（密钥配反、`.env` 双份）
都属于「实际是什么」与文档分岔，而没有任何视图能看出分岔。文档天生补不上这个洞。

## Goals / Non-Goals

- Goal：把运行时实况摆到一个页面上，尤其是**两份配置的并排指纹**
- Goal：密钥代际的判断以实测证据为准，不以变量名为准
- **Non-Goal**：不做告警、不做历史趋势。先让人能一眼看见，再谈自动化
- **Non-Goal**：不显示任何密钥、令牌的值

## Decisions

### D1：部署清单由部署脚本生成，而不是应用自省

应用无法可靠地知道自己是哪个 commit 构建的——`process.env` 里没有，
Next 的 standalone 产物也不带。让每个应用自己去猜会得到四个可能不一致的答案。

`deploy-mvp.sh` 在部署时写一份 `/opt/drsell-run/deploy-manifest.json`：
commit 短哈希、构建时刻、各应用关键配置项的指纹、迁移头。API 只读这一个文件。

**代价**：绕过部署脚本的手工改动不会反映在清单里。这是可接受的——
手工改动本来就该被视为异常，清单与实际不符恰好暴露了它。

### D2：指纹用 sha256 前 12 位

足以判断「两边一不一样」「是不是同一代」，且不可逆。长度也一并显示——
密钥被截断或多了引号时，长度是最快的线索。

### D3：API 读清单文件，不去读别的应用的 .env

让 API 去读 `apps/web/standalone/.../.env` 会把「谁能读谁的配置」这条边界弄脏，
而且在容器化或分机部署后立刻失效。指纹在部署时算好、写进清单，API 只读清单。

### D4：密钥代际只信 `WebhookSecretUse`

该表由真实入站 webhook 的验签结果填充。变量名不可信——2026-09-09 之前
`SHOPIFY_API_SECRET_PREVIOUS` 里放的才是当前密钥。

⚠ 该表只能由**真实 Shopify** 请求填充。自签探针会伪造出「已切换」的观测
（2026-09-09 污染过一次，已清表）。

## Risks / Trade-offs

**R1 — 清单可能过期（中）**
手工改配置后清单不更新，页面会显示旧指纹而看起来正常。
缓解：清单里带构建时刻，与 pm2 进程启动时刻并排显示；两者差距过大即可疑。

**R2 — 又一处要与实际保持一致的真相（中）**
清单本身可能与运行时分岔。缓解：清单在部署时由脚本从**实际写入的文件**算出，
不是从模板算的；且 `check-deploy-facts` 守住脚本仍在生成它。
